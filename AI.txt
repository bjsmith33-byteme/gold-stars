# AI Assistant Notes for this repo

## Design decisions (initial build prior to tracking)
Key choices behind the public "Gold Stars" site and why:

- This project started to take form early in the semester with an employer-internal site
  that I started working on at the same time as coming up with ideas for the web project.
  This file documents the decisions that were made prior to its creation and then further
  documents the decisions, additions, deletions, and edits, primarly made with Claude code
  for all functional changes until early-mid July, where these are tracked more discretely.
- Plain JavaScript / JSX (no TypeScript) — kept the code easy to read and hand-edit.
- React-Bootstrap (Bootstrap 5.3) — responsive/mobile-friendly out of the box; its
  Offcanvas powers the side-nav ("sheet" on mobile).
- React Router in declarative mode with HashRouter — GitHub Pages has no single-page-app
  fallback, so hash routes (#/kb, #/about) work without any server config or 404 redirect.
- Data is a single hand-editable CSV (public/gold-stars.csv) read live at runtime — no
  backend or database. Knowledge areas are React / JavaScript / CSS / SwiftUI; the roster
  is ~20 diverse fake names in src/lib/roster.js. All sample content is dummy data.
- One unified leaderboard (no team/sub-group split) to keep the public version simple.
- The "role" field is just a cosmetic specialty badge (Frontend/Backend/Mobile/Full-stack);
  it doesn't gate anything yet.
- Nominations are email-only (a mailto: from the Award form). A static public site has no
  backend and shouldn't expose direct data access, so a human reviews before adding a row.
  (Previously had allowed direct access to the csv for group members, but this version needs
  to be public.)
- Deploy model: build to docs/ with base "/gold-stars/"; GitHub Pages serves from /docs.
  Building does NOT publish — the site changes only when docs/ is committed and pushed
  (intentional, for control over when changes go live). No CI.
- Light/dark via Bootstrap's data-bs-theme, with a pre-paint script to avoid a flash.
- Contact/nomination email, the roster, and the CSV rows are PLACEHOLDERS to be replaced.

Which details to show, and how:
- One "gold star" per helpful contribution. The board shows the recipient, their
  role/specialty, the knowledge area, and a star count — recognition, never criticism.
- Standard competition ranking (ties share a place), tie-aware winners, and medals.
- The nominator (who gave the kudos) is stored but NOT shown on the board — it stays
  behind the scenes and instead powers a "Supporter of the Month" (top kudos-giver).
- Alongside the leaderboard: monthly winners, a per-knowledge-area breakdown to surface
  the growing expert in each area, a personal "My Stats" view (total, rank, a month-by-
  month trend, area mix, recent stars), and a Knowledge Base.
- Self-answers count if the person did the research; good questions are encouraged too.

How data is stored:
- A single flat file (CSV), one row per award, read live at view time — no backend or
  database. Columns: date, recipient, role, category, note, source, nominator, sub-topic.
- The note field does double duty: any row with a note becomes a Knowledge Base entry
  (problem -> solution), so the board and the KB share one source of truth.
- Chose a plain, hand-editable, version-controlled file for simplicity and transparency.

How data is collected:
- Primary: a web form that composes a row and hands it off by email, so a human reviews
  it before it's added — no direct write access to the data needed.
- Also explored auto-collecting stars from team-chat messages (a message with a star and
  who it's for). Lesson learned: the chat platform's API returned only ONE reaction per
  message, so reading emoji *reactions* was unworkable — the design switched to parsing
  message *text + mentions*, pulled on a schedule, with a watchdog to alert on failed runs.
  This feature is not included in the public version.

Future ideas discussed (not all built):
- Recognize learners, not just answerers — a "Learner of the Month" for the best
  question-askers (needs capturing who asked).
- Optional email-on-award to the recipient and/or their manager/lead.
- A dedicated, searchable Knowledge Base page (built in this public version).
- A curated "Question of the Month"; an automated summarizer to turn raw Q&A into clean
  KB notes; a personal "curiosity" stat (questions asked that became KB entries).

Ideas considered and rejected (and why):
- A wiki-style page — no dynamic data or aggregation.
- A reporting/BI summary page — not self-service; needed platform-team setup.
- Reading chat emoji reactions via the platform API — only one reaction per message.
- A popular test runner whose binary was blocked in the environment — used the language's
  built-in test runner instead.
- For this public version specifically: dropped the team/sub-group ("Friends") split for
  simplicity, and dropped chat + direct-file editing in favor of email-only nominations.
